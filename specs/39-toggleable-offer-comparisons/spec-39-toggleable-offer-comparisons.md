- **Objective:** Compare the current editable offer with available historical proposals, mediator-reported counteroffers, and persisted scenario values while retaining the asset-level table as the exact review/edit surface.
- **Scope:** Read-only comparison data in the existing offer-response model, a responsive chart with independent series controls, and an asset comparison/edit table for the authenticated case workflow. No new offer lifecycle, database column, credit, AI, or legal/fairness analysis is introduced.

## Functional requirements

- **FR-39-01 — Shared, correctly labeled history:** Use the same comparison surface for initial incoming offers and later counteroffer attempts. Respect `offer_origin`. An initial incoming offer shows its saved intake notes/asset terms and does not create a prior-user-proposal series or infer amounts from free text. A later attempt shows the predecessor's recorded proposal and counteroffer when present, distinct from the current attempt's editable proposal.
- **FR-39-02 — Available series:** Independently toggle these chart series: user's baseline, user's current scenario value, opposing-party baseline, opposing-party current scenario value, prior user proposal, the counteroffer that preceded this attempt (or the current response when there is no predecessor), a separately reported current-attempt counteroffer when both exist, user's projected allocation if the preceding counteroffer were accepted, and current editable user proposal. Unavailable series have visible reasons and disabled toggles; they are never populated with guessed values.
- **FR-39-03 — Baselines stay explicit:** The current attempt model has no explicit per-asset starting-baseline snapshot. Until one is persisted, both baseline series remain unavailable with that explanation. Do not treat the first ledger event or another date as a baseline.
- **FR-39-04 — Scenario values:** Derive per-asset party values deterministically from the attempt's saved scenario balances and saved community-share assumption. Debts are negative. Unresolved balances are excluded from party allocations and marked as partial/unresolved in the chart, table, and totals; they are not assigned to either party.
- **FR-39-05 — Proposal and counteroffer values:** Current and predecessor proposals use their persisted `proposed_values`; counteroffers use `counteroffer_json`. Prefer the predecessor's counteroffer as the comparison that led to the current attempt; when the current attempt has since received another response, keep those two counteroffer records in separate series. Preserve source, attempt ordinal, proposal-version ordinal, record time when present, and `verified_by_app: false` for reported counteroffers. The projected-if-accepted series repeats the exact preceding counteroffer amount for that asset (or the current response when no predecessor counteroffer exists), clearly labeled as unverified and not as an acceptance prediction.
- **FR-39-06 — Table and deterministic arithmetic:** Keep an accessible per-asset table for scenario values, baselines, prior proposal, counteroffer, projected allocation, differences, and the editable current proposal. Recompute known subtotals, complete totals, and per-asset/aggregate differences from persisted comparison values; incomplete totals or differences remain unavailable or explicitly partial. Editing the current proposal updates the existing attempt state only.
- **FR-39-07 — Toggle isolation:** Toggling a chart series changes chart visibility only. It does not update the table's values, proposal inputs, attempt revision, saved records, or snapshots.
- **FR-39-08 — Immutable history and finalization:** Never rewrite predecessor state, frozen snapshots, or `finalized_snapshot_json`. Finalized attempts remain read-only; a new attempt is an independent editable copy under Specs 22/24/35/37.
- **FR-39-09 — No AI or legal conclusions:** Comparison and arithmetic are available without AI. The UI does not claim that a counteroffer is verified, accepted, fair, or legally effective.
- **FR-39-10 — Accessibility and responsive layout:** Provide labeled native checkboxes, keyboard-operable controls, visible unavailable states, a textual chart companion, and a semantic asset table. Keep the table in a labeled horizontally scrollable region on narrow screens; keep chart bars and labels usable without color.

## Acceptance criteria

1. Initial incoming offer notes remain visible and no user proposal is invented; later attempts distinguish the current proposal, predecessor proposal, and mediator-reported counteroffer.
2. Each available chart series can be toggled independently; missing baseline, unrecorded amount, and unresolved portions remain visibly unavailable.
3. Scenario allocations, totals, differences, and counteroffer projections are deterministic and traceable to persisted values and assumptions.
4. The table edits only the current proposal; chart toggles do not change values. A newly reported counteroffer never replaces the predecessor's counteroffer in the same comparison.
5. Prior proposal data and finalized/frozen snapshots remain unchanged after comparison or current-attempt edits.
6. Mobile/keyboard/screen-reader controls expose the same information as the chart.
7. No migration or AI request is required for comparison.

- Focused coverage: `tests/test_offer_comparison.py`, `tests/test_counteroffer_workflow.py`, `tests/test_existing_offer.py`, and `tests/test_offer_response.py` pass.
- Migration status: none. This reuses `counteroffer_json`, existing attempt editable state and snapshots, and the persisted scenario result.
- Full suite: 433 tests ran; one existing failure remains in `test_main.MainWorkflowTests.test_theme_selection_persistence_and_shared_page_coverage`. Its color-token regex rejects the pre-existing `#17241f` CSS value, which is present in `origin/main`.
- Known limitation: the current data model does not persist explicit per-asset starting baselines, so baseline series are intentionally unavailable. User-reported free-text incoming terms remain informational until values are explicitly recorded against assets.
