# Spec 38: Preserve Work and Recover from Processing Failures

- **Status:** Implemented; focused tests passing; full suite has one known pre-existing theme-token failure
- **Related issue:** [#125 — Preserve work and restore attempt credit on upload, analysis, or generation failure](https://github.com/whyi/WA-contested-divorce-without-children-mediation-to-end/issues/125)
- **Related specifications:** [Spec 07: Asynchronous Document Extraction](../07-asynchronous-document-extraction/spec-07-asynchronous-document-extraction.md), [Spec 08: Consent-Based Document Analysis](../08-consent-based-document-analysis/spec-08-consent-based-document-analysis.md), [Spec 33: Existing Opposing Offer Intake](../33-existing-offer-intake/spec-33-existing-offer-intake.md), [Spec 35: Attempt Finalization and Snapshot](../35-attempt-finalization-snapshot/spec-35-attempt-finalization-snapshot.md), [Spec 36: Attempt Credits](../36-attempt-credit-packages/spec-36-attempt-credit-packages.md)
- **Superseded historical requirements:** No historical spec is edited and no prior requirement is narrowed. This spec makes Spec 33 FR-33-09's retry guarantee explicit across reload, superseding only the former in-memory-only implementation: intake retry identifiers and unsaved offer notes/answer are retained for the current browser tab, and recovery reconciles an already-persisted upload before retrying.
- **Objective:** Keep source material and editable attempt work recoverable when upload, extraction, consented AI analysis, or final proposal generation fails; make retry explicit and safe without introducing refunds for undeducted entitlements.
- **Scope:** Client retry recovery for offer uploads, safe retry of failed extraction and AI-analysis jobs, and verification of existing finalization rollback/idempotency. Detailed failure-specific UX, operations/on-call work, external storage repair and manual-entry fallbacks are deferred.

## Requirements

- **FR-38-01 — Upload recovery:** Upload errors are reported as failures. The case and its saved data remain intact. Before a source upload is acknowledged as persisted, the browser retains the pending offer answer, notes, file identity, and batch/item idempotency keys in tab-scoped storage. On reload, notes and retry identity are restored; if the server already has the item, it is reconciled and reused. If it does not, the user is asked to reselect the same file; a different file receives new item identity. The server binds an existing item key to the persisted source digest and rejects reuse for different contents. No duplicate document record is created on a retry of the same item. Successful save clears recovery state.
- **FR-38-02 — Extraction recovery:** A case-authorized, CSRF-protected retry action may requeue only a `failed` extraction job whose document and source digest still match. Retry uses the existing job/request identity, resets its transient failure state, and never duplicates the source document. `needs_attention` conditions (for example unsupported or unreadable sources) remain explicit and are not represented as a successful retry.
- **FR-38-03 — Analysis failure and consent:** Analysis continues to require the existing explicit, current consent. Request/job status and safe error codes are persisted and reported; failed jobs may be retried only against the same case, document digest, and active consent. No failed/partial response is represented as completed, and no empty-analysis fallback is substituted. Retry creates no new consent or duplicate source document.
- **FR-38-04 — Final proposal failure:** Draft generation is free. Rendering, validation, size, stale revision, or persistence failure leaves the attempt editable and its current server-persisted inputs unchanged. A failed transaction has no partial proposal version or finalization snapshot.
- **FR-38-05 — Attempt entitlement accounting:** Preserve Spec 36: the first successful finalized attempt is free; only later successful finalizations debit one credit, atomically with snapshot commit. A failed/cancelled finalization neither consumes the free-first entitlement nor debits a credit. Since failures roll back the debit transaction, no refund is issued for an undeducted entitlement. Repeated finalization/download of the same attempt cannot debit or restore twice.
- **FR-38-06 — Authorization and privacy:** Existing authentication, active case authorization, CSRF, case locking, idempotency, no-store responses, consent, source digest checks and cross-case isolation remain in force. Browser recovery state is tab-scoped, contains no file bytes or provider secrets, and is cleared after successful save.
- **FR-38-07 — Explicit retry and no partial success:** Failure status remains visible and the affected operation is retryable where its source and prerequisites remain valid. The UI does not claim that a failed upload, analysis, or generation succeeded.

## Acceptance criteria

1. A failed or interrupted offer upload preserves notes and retry identity across refresh; a reselected same file reuses the idempotency keys, while an already-persisted item is recovered without uploading a second document. Reusing an item key with different bytes returns 409 and stores nothing.
2. A failed extraction job can be retried through an authorized route; other statuses and a changed/missing source cannot be retried as if successful.
3. Analysis failure is explicit and retryable only under active consent for the same source; completed/partial/failed statuses remain distinct.
4. Proposal rendering or persistence failure leaves the attempt editable and does not commit a partial version, snapshot, debit, or free-first consumption.
5. Repeating a successful finalization remains free and idempotent; existing successful behavior is unchanged.

## Implementation and verification

- Client recovery: `src/app/static/index.html`; upload idempotency is bound to the source SHA-256 in `src/app/materials.py`; extraction retry route: `src/app/main.py`; retry policy: `src/app/extraction.py`.
- Focused coverage: `tests/test_failure_recovery.py`, `tests/test_extraction.py`, `tests/test_analysis.py`, `tests/test_analysis_worker.py`, `tests/test_materials.py`, and `tests/test_attempt_finalization.py`.
- Migration: none. Recovery uses existing persisted job, import, attempt, and credit records.
- Limitations: after a browser reload, browsers do not expose the selected file bytes; the UI preserves the file identity and asks the user to reselect the same file when upload had not committed. External object-store cleanup after a failed transaction remains best-effort; retries remain idempotent at the document-record boundary. The full suite reports 425 tests with one baseline failure in `test_main.MainWorkflowTests.test_theme_selection_persistence_and_shared_page_coverage`: its regex treats existing hard-coded `#17241f` colors (also present in `origin/main`) as theme tokens.
