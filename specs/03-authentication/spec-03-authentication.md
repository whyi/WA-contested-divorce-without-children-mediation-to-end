# Spec 03: Authentication, Sessions, and Account Security

- **Status:** Draft for review
- **Related issue:** [#21 — Implement User Signup, Login, Social Auth, and MFA/Passkey Foundation](https://github.com/whyi/WA-contested-divorce-without-children-mediation-to-end/issues/21)
- **Objective:** Define an authentication foundation for user registration,
  sign-in, social identity, MFA, passkeys, and session lifecycle.
- **Security boundary:** Authentication establishes control of an account. It
  does not establish that the account holder is a named party or legal
  representative, nor does it grant access to any case. Case-level
  authorization must be enforced separately before case data is returned or
  changed.
- **Implementation gate:** This specification is a proposal. Provider,
  deployment, email-verification, and token-transport decisions listed in
  Section 9 require approval before production authentication is enabled.

## 1. Scope

### 1.1 In scope

- Local account registration and email/password sign-in.
- Google sign-in using OpenID Connect (OIDC).
- Access and refresh token issuance, rotation, revocation, and logout.
- Optional TOTP-based multi-factor authentication.
- WebAuthn passkey registration and authentication.
- Persistent user, identity, credential, and session records.
- Rate limiting, account recovery, audit events, and security tests required
  to operate the authentication flows safely.

### 1.2 Out of scope

- Verifying a user's legal identity, party status, or representative authority.
- Automatically granting access to a case based only on sign-up, email
  address, or social-provider profile.
- Case-specific roles and authorization policy beyond defining the required
  integration boundary.
- Google Drive, OneDrive, Dropbox, AI, offer, and email-to-opposing-party
  workflows.
- Enterprise SSO, additional social providers, SMS-based MFA, and account
  federation beyond Google OIDC.

## 2. Authentication States and Account Lifecycle

An account has an explicit lifecycle:

1. `PENDING_VERIFICATION`: The account is created, but the email address has
   not been verified. The account may complete verification and sign in, but
   it must not access case data.
2. `ACTIVE`: The account has a verified email and may authenticate. Case data
   remains subject to case-level authorization.
3. `LOCKED`: Sign-in is temporarily denied after configured abuse or
   administrator action. The user receives a generic message that does not
   expose internal detection signals.
4. `DISABLED`: Sign-in is denied and active sessions are revoked.

MFA enrollment is represented separately from account lifecycle. When a user
has enabled MFA, successful password or social authentication alone is
insufficient to complete sign-in; a valid configured second factor is also
required.

## 3. Functional Requirements

### 3.1 Signup and email verification

- **FR-03-01 — Local signup:** `POST /api/auth/signup` must accept an email
  address and password, validate both, create a local account, and return a
  non-sensitive account response. It must not return password material,
  credentials, or tokens for an unverified account.
- **FR-03-02 — Email normalization and uniqueness:** The system must normalize
  email addresses consistently and enforce uniqueness for the normalized
  address at the database level. Email normalization must not remove
  provider-specific mailbox semantics such as dots or plus tags.
- **FR-03-03 — Email verification:** Signup must initiate email verification
  using a single-use, time-limited, cryptographically random verification
  token. Only a verified account may become `ACTIVE`. Verification tokens
  must be stored as hashes, expire, and be invalidated after successful use.
- **FR-03-04 — Signup enumeration resistance:** Responses and timing for
  duplicate-address signup attempts must not disclose whether an account
  exists. Any verification message must use a consistent response shape.
- **FR-03-05 — Password policy:** Passwords must be validated server-side
  against a documented minimum length and maximum input size. The policy must
  reject commonly breached or trivially weak passwords. Composition rules
  must not be used as a substitute for length and breached-password checks.
  Final numeric limits and the breached-password-check mechanism require
  approval before implementation.
- **FR-03-06 — Password storage:** Passwords must be hashed with Argon2id and
  a deployment-approved work factor. Per-password salts must be generated by
  the hashing library. Plaintext passwords and reusable password-equivalent
  values must never be stored or logged.

### 3.2 Login, tokens, and session management

- **FR-03-07 — Local login:** `POST /api/auth/login` must authenticate an
  active account with a local password and return a generic failure for an
  invalid email/password pair. Error responses must not reveal whether the
  account exists, is unverified, or has an incorrect password.
- **FR-03-08 — MFA challenge:** When an account has MFA enabled, password or
  social authentication must produce a short-lived, single-use, restricted
  challenge. The system must not issue a fully authenticated session until an
  enrolled second factor has been verified.
- **FR-03-09 — Access token:** Successful authentication must issue a signed
  access JWT with a unique token identifier, subject, issuer, audience,
  issued-at, and expiration claims. The server must validate the configured
  algorithm, key, issuer, audience, and time claims; it must reject unsigned
  tokens and algorithm substitution.
- **FR-03-10 — Refresh token:** Successful authentication must issue a
  signed refresh JWT associated with a persisted server-side session. It must
  have a unique token identifier, subject, issuer, audience, issued-at, and
  expiration claims. Refresh JWTs must rotate on each successful use. Reuse of
  a previously rotated refresh JWT must revoke the affected session family
  and require reauthentication.
- **FR-03-11 — Token transport:** Browser refresh credentials must be
  transported in `Secure`, `HttpOnly`, appropriately `SameSite` cookies and
  protected against cross-site request forgery for state-changing requests.
  Access and refresh tokens must not be stored in browser local storage.
  Exact access-token transport and CSRF strategy must be documented for each
  supported client.
- **FR-03-12 — Refresh and logout endpoints:** The API must provide refresh
  and logout operations. Logout must revoke the server-side session and
  expire the corresponding browser cookie. Refresh must fail closed for
  revoked, expired, malformed, or reused tokens.
- **FR-03-13 — Session limits and expiry:** The system must support
  configurable idle and absolute session expiry, per-user active-session
  limits, and revocation of all sessions after password reset, account
  disablement, or a confirmed credential compromise. Initial duration and
  limit values require approval.
- **FR-03-14 — Account recovery:** The system must provide a secure password
  reset flow using single-use, time-limited, hashed tokens. Password reset
  must revoke existing sessions and must not automatically disable or bypass
  MFA. Responses must not disclose account existence.

### 3.3 Social login

- **FR-03-15 — Google OIDC:** The system must support Google as the initial
  social identity provider using OIDC Authorization Code flow with PKCE.
  Authentication requests must use and validate `state` and `nonce`; ID
  tokens must be validated for signature, issuer, audience, expiry, and nonce.
- **FR-03-16 — Provider account mapping:** External identities must be keyed
  by provider and immutable provider subject identifier, not email alone.
  Provider email may be used for contact or account discovery only after
  validation of its verification status.
- **FR-03-17 — Safe account linking:** A social identity must not be silently
  linked to an existing local account solely because the email strings match.
  Linking an additional provider to an existing account must require an
  authenticated, explicit account-linking flow and recent reauthentication.
- **FR-03-18 — Provider failure:** Cancelled, malformed, expired, or
  unverifiable provider responses must not create an authenticated session or
  a partially linked identity. The user must receive a safe, actionable error.
- **FR-03-19 — Provider credentials:** The application must never ask for or
  store a user's Google password. OAuth client secrets and signing keys must
  be supplied through deployment secret management and must not be committed
  to source control.

### 3.4 TOTP MFA

- **FR-03-20 — TOTP enrollment:** An active user must be able to begin TOTP
  enrollment and receive the provisioning information needed by a compatible
  authenticator app. MFA must remain pending until the user submits a valid
  time-based code.
- **FR-03-21 — TOTP secret protection:** TOTP shared secrets must be
  encrypted at rest using deployment-managed encryption keys. They must not
  be included in logs, normal account responses, or database exports as
  plaintext.
- **FR-03-22 — TOTP verification:** Codes must be checked within a
  configurable clock-skew window, with single-use replay prevention and
  rate limiting. A valid code must be required for MFA login and for
  security-sensitive account changes.
- **FR-03-23 — Disable MFA:** Disabling TOTP must require recent
  reauthentication and a valid current factor or an approved recovery
  procedure. The action must revoke existing sessions and produce an audit
  event.
- **FR-03-24 — Recovery codes:** If recovery codes are provided, they must be
  generated from cryptographically secure randomness, displayed only once,
  stored as hashes, individually single-use, and replaceable only after
  reauthentication.

### 3.5 WebAuthn passkeys

- **FR-03-25 — Passkey registration:** An authenticated user must be able to
  register a passkey through WebAuthn. The server must issue a
  cryptographically random, short-lived, single-use challenge bound to the
  user and expected operation.
- **FR-03-26 — Passkey verification:** The server must validate the WebAuthn
  challenge, origin, relying-party ID, credential type, signature, user
  verification policy, and authenticator data before accepting an assertion.
  Challenges must be invalidated after use or expiry.
- **FR-03-27 — Passkey data:** The system must store only public credential
  material and required metadata, including credential ID, public key,
  sign-counter/authenticator metadata where applicable, transports if
  provided, creation time, and user-assigned display name. It must never
  receive or store a passkey private key.
- **FR-03-28 — Passkey lifecycle:** Users must be able to list and revoke
  their registered passkeys after reauthentication. Revocation must prevent
  future assertions from authenticating and must be audited.
- **FR-03-29 — Recovery and fallback:** Passkey loss must not silently
  disable account protections. Recovery must use a separately authenticated
  method and must not bypass configured MFA without an explicit recovery
  policy.

### 3.6 Authorization and audit

- **FR-03-30 — Case-access separation:** Authentication middleware must make
  the verified account identifier available to downstream authorization.
  Case and document endpoints must verify an explicit case-access grant
  before reading or mutating data. A signed-in user without a grant must
  receive no case content.
- **FR-03-31 — No implicit case grants:** Signup, email verification, social
  login, account linking, and MFA enrollment must not grant access to existing
  cases. Case-owner assignment and membership migration must be separately
  defined and tested before case endpoints are enabled.
- **FR-03-32 — Security audit events:** The system must record time-ordered,
  attributable events for signup, verification, login success/failure,
  refresh/reuse detection, logout, password reset, provider linking, MFA and
  passkey changes, account lock/disablement, and session revocation. Audit
  events must not contain passwords, tokens, OTP values, recovery codes,
  private keys, or OAuth client secrets.

## 4. Data Model Requirements

The database must enforce uniqueness and referential integrity for identity
and credential records. At minimum, the model must represent:

- **`users`**: UUID, normalized email, email-verification status and timestamp,
  lifecycle status, optional password hash, created/updated timestamps.
- **`external_identities`**: UUID, user ID, provider key, immutable provider
  subject, provider email and verification metadata where needed, created
  timestamp; unique constraint on `(provider, provider_subject)`.
- **`auth_sessions`**: UUID, user ID, refresh-token/JWT identifier hash,
  session-family identifier, created/last-used/expiry/revocation timestamps,
  rotation/reuse metadata needed to revoke a token family.
- **`totp_credentials`**: UUID, user ID, encrypted secret, activation and
  revocation timestamps, last accepted time-step or equivalent replay
  protection state.
- **`passkey_credentials`**: UUID, user ID, unique credential ID, public key,
  sign-counter and authenticator metadata, display name, created/last-used/
  revoked timestamps.
- **`verification_tokens` and `password_reset_tokens`**: user ID, token hash,
  expiry, use/revocation timestamps, and purpose.
- **`auth_audit_events`**: event type, actor/user identifier when known,
  timestamp, outcome, and minimal non-secret context.
- **`case_memberships` or equivalent authorization record**: account ID,
  case ID, role, grant/revocation timestamps, and grant provenance, if case
  APIs are to be enabled as part of this work.

Password hashes, encrypted TOTP secrets, public passkey keys, and token hashes
must use separate fields and explicit handling. Deleting or disabling a user
must not leave active credentials or sessions usable.

## 5. API Contract

The implementation must publish request/response schemas and error contracts
for at least:

- `POST /api/auth/signup`
- `POST /api/auth/verify-email`
- `POST /api/auth/verify-email/resend`
- `POST /api/auth/login`
- `POST /api/auth/refresh`
- `POST /api/auth/logout`
- `POST /api/auth/password/forgot`
- `POST /api/auth/password/reset`
- `GET /api/auth/oidc/google/start`
- `GET /api/auth/oidc/google/callback`
- `POST /api/auth/mfa/totp/enroll`
- `POST /api/auth/mfa/totp/confirm`
- `POST /api/auth/mfa/totp/verify`
- `POST /api/auth/mfa/totp/disable`
- `POST /api/auth/passkeys/register/options`
- `POST /api/auth/passkeys/register/verify`
- `POST /api/auth/passkeys/authenticate/options`
- `POST /api/auth/passkeys/authenticate/verify`
- `GET /api/auth/passkeys`
- `DELETE /api/auth/passkeys/{credential_id}`
- `GET /api/auth/sessions`
- `DELETE /api/auth/sessions/{session_id}`

Responses must avoid returning secret material and must not distinguish
account existence during signup, login, password-recovery, and verification
flows where that would enable enumeration.

## 6. Non-Functional and Security Requirements

- **NFR-03-01 — Transport security:** All non-local deployments must use HTTPS.
  Authentication cookies must be `Secure`; credentials and tokens must never
  be sent in URL query parameters.
- **NFR-03-02 — Abuse resistance:** Signup, login, verification, reset,
  refresh, MFA, and WebAuthn challenge endpoints must have rate limits and
  abuse monitoring. Limits must be configurable and return safe retry
  guidance.
- **NFR-03-03 — Secret management:** Signing keys, OAuth client secrets,
  encryption keys, and email-provider credentials must come from a managed
  secret source. Key rotation must be supported without accepting
  unapproved algorithms or invalid signatures.
- **NFR-03-04 — Data minimization:** Authentication responses, application
  logs, and audit events must exclude passwords, bearer tokens, refresh
  tokens, OTPs, recovery codes, private keys, and unnecessary provider
  profile data.
- **NFR-03-05 — Availability and fail-closed behavior:** If token validation,
  session lookup, or required authentication storage is unavailable, protected
  endpoints must deny access rather than continue anonymously.
- **NFR-03-06 — Compatibility:** Password hashing parameters and token key
  identifiers must support safe upgrades and rotation without silently
  weakening stored credentials or accepting obsolete token algorithms.

## 7. Acceptance Criteria

- A new user can register with a valid email and policy-compliant password;
  invalid input is rejected and no plaintext password is stored.
- A user must verify their email before obtaining a session that can access
  protected functionality.
- Valid credentials authenticate; invalid credentials produce a generic
  response and are rate limited.
- Access and refresh tokens have validated claims, bounded lifetime, and
  persisted revocation state. Refresh rotates tokens; replay revokes the
  session family.
- Google OIDC sign-in validates protocol state and token claims and maps the
  provider subject to exactly one external identity record.
- A matching email alone cannot silently link a social identity to an
  existing account.
- An enrolled TOTP factor is required to complete login; invalid, replayed,
  expired, and over-rate codes are rejected.
- TOTP enrollment and disablement require confirmation and reauthentication;
  secrets are encrypted and recovery codes, if issued, are single-use.
- Passkey registration and authentication reject invalid challenges, origins,
  relying-party IDs, signatures, and replayed challenges.
- Passkey private keys are never sent to or stored by the server.
- Logout, password reset, account disablement, and credential revocation
  invalidate the applicable sessions.
- An authenticated user without an explicit case-access grant cannot read or
  modify a case or its documents.
- Authentication tests cover unit, API integration, database migration,
  session rotation/reuse, provider callback failure, MFA, passkey, and
  authorization-denial scenarios.
- No production environment can enable case-data endpoints with a bypass or
  default identity when authentication configuration is missing.

## 8. Required TDD and Rollout

1. Add tests for schemas, password policy, token validation, account
   lifecycle, and endpoint response contracts.
2. Run focused tests and observe expected failures before implementation.
3. Implement and validate signup, verification, local login, session
   persistence, refresh rotation, logout, and password recovery.
4. Integrate Google OIDC with mocked protocol responses and a provider
   configuration test; do not require live credentials in unit tests.
5. Add TOTP enrollment, verification, recovery, and revocation.
6. Add WebAuthn registration/authentication challenge flows and validation
   tests.
7. Integrate case-membership authorization and verify denial for unassigned
   accounts before enabling case/document routes.
8. Run migration upgrade/downgrade checks, the complete test suite, and
   configuration checks before rollout.

Roll out authentication endpoints before enabling case-data endpoints.
Protected data endpoints must remain unavailable until identity validation,
session validation, case-level authorization, and ownership handling for
existing records are all in place.

## 9. Decisions Required Before Implementation

The following are proposed safe defaults, not approved product decisions:

- **Password hashing:** Argon2id through a maintained password-hashing
  library, with work factors benchmarked for the deployment environment.
- **Social provider:** Google OIDC first; add Apple or Microsoft only through
  a separately tested provider configuration.
- **Web sessions:** Short-lived access JWT plus rotating refresh token bound
  to a persisted server-side session; browser refresh token in a secure
  HttpOnly cookie.
- **Email verification and recovery:** Required before case access, with
  single-use expiring links delivered by an approved transactional email
  provider.
- **TOTP:** Optional account enrollment; required on sign-in after the user
  enables it.
- **Passkeys:** Support as a phishing-resistant authentication method and
  optional second factor; retain a clearly specified recovery path.
- **MFA policy:** Whether MFA is optional for all users or required for
  selected actions/accounts.
- **Token policy:** Access and refresh lifetimes, session limits, idle timeout,
  and absolute timeout.
- **Deployment:** Production domains, HTTPS termination, cookie domain,
  allowed origins, secret manager, signing-key rotation, and WebAuthn
  relying-party ID.
- **Email operations:** Verification/reset delivery provider, message
  templates, delivery failure behavior, and anti-enumeration response
  requirements.
- **Existing cases:** How ownership or membership is assigned to pre-existing
  cases before protected APIs are re-enabled.
- **Privacy and retention:** Retention and deletion periods for user profiles,
  login/audit events, verification/reset records, and revoked credentials.
- **Accessibility and localization:** Login, MFA, passkey fallback, and
  recovery requirements for assistive technology and supported languages.
